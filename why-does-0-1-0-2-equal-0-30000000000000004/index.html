Why Does 0.1 + 0.2 Equal 0.30000000000000004?

The result is not a random JavaScript bug. It is a consequence of representing many decimal fractions using a finite number of binary digits. This guide explains the representation, shows the calculation, and gives practical ways to handle precision.

An educational guide from PANKRI · Published November 3, 2026

Decimal fractions are not always exact in binary

Humans commonly write numbers in base 10. Computers represent ordinary floating-point values in base 2. Just as one third repeats forever in decimal (0.3333…), one tenth repeats forever in binary. A finite computer format must round that repeating expansion to a nearby representable value.

IEEE 754 binary floating-point stores a sign, an exponent and a significand. The format has finite precision, so most decimal fractions cannot be stored exactly. The stored value for a source literal such as 0.1 is therefore a close binary approximation, not the exact mathematical fraction one tenth.

What happens when JavaScript adds 0.1 and 0.2?

JavaScript's ordinary Number type uses IEEE 754 binary64 floating-point. The values represented by the literals 0.1 and 0.2 are approximations. Adding those approximations produces a binary64 value whose shortest familiar decimal rendering is 0.30000000000000004.

console.log(0.1 + 0.2);
// 0.30000000000000004

console.log((0.1 + 0.2) === 0.3);
// false

The arithmetic is consistent with the selected representation. The surprising part is expecting a finite binary format to preserve every base-10 fraction exactly.

Why exact equality can be unsafe for fractional calculations

When a calculation involves measured or fractional values, exact equality may be too strict. A common approach is to compare the absolute difference against a tolerance chosen for the scale and error characteristics of the problem.

function nearlyEqual(a, b, epsilon = 1e-10) {
  return Math.abs(a - b) < epsilon;
}

nearlyEqual(0.1 + 0.2, 0.3); // true

This simple absolute tolerance is useful for values near the same scale. For values spanning very different magnitudes, consider a combined absolute and relative tolerance. Do not choose an arbitrary epsilon without considering the units, scale and acceptable error in your application.

How should applications handle money?

Do not assume binary floating-point is suitable for every monetary calculation. Common approaches include storing amounts as integer minor units (for example, paise or cents), using a decimal arithmetic library, and applying an explicitly documented rounding rule at defined boundaries. The correct choice depends on currency precision, tax rules and the domain.

For example, storing ₹12.34 as 1234 paise avoids representing that amount as a binary floating-point fraction during simple addition. It does not, by itself, solve every currency, exchange-rate or tax-rounding problem.

Key takeaways

  • Binary floating-point cannot represent many decimal fractions exactly.
  • 0.1 + 0.2 exposes normal rounding behavior, not a random failure.
  • For approximate numeric results, compare with a tolerance suited to the problem.
  • For money, use integer minor units or an appropriate decimal representation and explicit rounding rules.

Frequently asked questions

Is 0.1 + 0.2 a JavaScript bug?

No. JavaScript Number follows IEEE 754 binary64 arithmetic. The displayed result is a consequence of finite-precision binary representation and rounding.

Does every programming language have this issue?

Many languages that use binary floating-point for ordinary decimal literals exhibit similar behavior. Exact details and formatting vary by language and numeric type.

Should I always use epsilon to compare numbers?

No single tolerance works for every problem. Choose absolute or relative tolerances based on magnitude, units and acceptable error. For exact domains, use an exact representation instead.
