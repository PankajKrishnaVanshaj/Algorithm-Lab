Big O Notation: A Practical Guide to Algorithm Complexity

Big O notation describes how an algorithm’s resource requirements grow as input size increases. Learn the common complexity classes and connect them to algorithms you can run in PANKRI Algorithm Lab.

What Big O describes

Big O expresses an upper-bound growth rate while abstracting away constant factors and lower-order terms. It helps compare how algorithms scale as input size grows. It does not directly predict milliseconds, and two O(n log n) algorithms can have different constants, memory needs and real-world performance.

Common time complexity classes

O(1) is constant growth, as with reading an array element by index. O(log n) is logarithmic, as with Binary Search on sorted random-access data. O(n) is linear, as with scanning every element once. O(n log n) appears in efficient comparison sorting such as Merge Sort and average-case Quick Sort. O(n²) appears in simple nested-loop algorithms such as basic Bubble Sort.

Time complexity versus space complexity

Time complexity describes how the number of operations grows with input size. Space complexity describes how additional memory requirements grow. An algorithm may trade memory for speed: Merge Sort uses additional storage to merge sorted halves, while common in-place Quick Sort implementations reduce array storage needs but use recursion stack space.

Best, average and worst cases

The best case describes the most favorable input of a given size, the worst case describes the least favorable, and average-case analysis depends on assumptions about input distributions. Always state which case is being discussed. For example, optimized Bubble Sort can be O(n) on an already sorted array but O(n²) on average and in the worst case.

Compare growth, not just one input

Consider two simplified algorithms. One performs about 3n operations; another performs about n². At n = 10, these estimates are 30 and 100. At n = 1,000, they are 3,000 and 1,000,000. The constants matter for real implementations, but the quadratic term grows much faster as the input becomes large.

Big O suppresses constant factors and lower-order terms when describing asymptotic upper growth. For example, 7n² + 4n + 20 is O(n²). That does not mean the 7, the 4 or the 20 are irrelevant to measured performance at practical input sizes. It means the n² term dominates the growth for sufficiently large n.

Big O, Big Theta and Big Omega

Big O gives an asymptotic upper bound, Big Omega gives a lower bound, and Big Theta describes a tight bound when both an upper and lower bound of the same growth class apply. Informal discussions sometimes use “Big O” as shorthand for an algorithm's typical complexity, but a rigorous explanation should state the case being analyzed and the assumptions about input and implementation.

For example, optimized Bubble Sort can finish in linear time on an already sorted array if it detects a pass with no swaps. Its average and worst-case time remain quadratic. Saying simply “Bubble Sort is O(n²)” is useful shorthand for common average/worst-case discussion, but it hides the best-case behavior and the optimization assumption.

Count the right input and the right memory

For an array, n often means the number of elements. For a graph, the useful variables are usually V vertices and E edges. For a matrix, dimensions such as rows and columns may both matter. Avoid hiding an important second dimension inside a single n when the algorithm's work depends on both.

Also state what “space” means. Auxiliary space usually means extra working memory beyond the input representation; total space may include the input itself, output structures and recursion stack. An iterative algorithm can avoid recursive stack growth, while a recursive algorithm's call depth may itself depend on input shape.

Common ways complexity is misread

  • Confusing asymptotic growth with elapsed time or a benchmark score.
  • Quoting average-case complexity without explaining the expected input or randomization assumption.
  • Ignoring input shape when an algorithm has a strong best/worst-case difference.
  • Comparing two operation counters that count different kinds of work as if each operation had equal machine cost.
  • Leaving out recursion stack, temporary arrays or other auxiliary storage.

Frequently asked questions

Does O(n) always mean faster than O(n log n)?

For sufficiently large n, linear growth eventually grows more slowly than n log n, but actual runtime at small sizes also depends on constants, memory access and implementation overhead.

Is Big O the same as runtime?

No. Big O describes asymptotic growth, not a measured duration. Runtime measurements require controlled benchmarks on specified hardware and software.

What is the difference between O(n) and O(1) space?

O(1) auxiliary space stays bounded as input grows. O(n) auxiliary space grows proportionally with the input size, excluding or including input storage according to the stated convention.
